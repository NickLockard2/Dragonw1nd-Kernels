`clang_version=manifest` deliberately uses the Clang toolchain committed in the
pinned OnePlus/CodeLinaro manifest. An initial build with the newer external
`aosp-clang-r614150` toolchain failed because Clang 23 promotes legacy OnePlus
driver declarations to fatal `-Wstrict-prototypes` errors. The phone's stock
5.15.197 kernel identifies Android Clang 14.0.7 (`r450784e`), so the manifest
toolchain is the compatibility- and provenance-preserving choice; no driver
warning suppression or behavioral source patch is applied.

The OP11 device configuration requests `-mtune=cortex-a715`, but Android
Clang 14.0.7 predates that CPU name and rejects the option. The build action
therefore compiles a minimal AArch64 probe with the selected compiler and adds
the optional `-mtune` only when supported. With the stock-matched manifest
compiler it uses Clang's default AArch64 tuning. This changes optimization
tuning only; it does not suppress diagnostics, modify driver behavior, or
change the pinned source revisions.

The earlier community vendor revision
`39a624900edc01caa28a806c80828e9cc17ac92d` diverged before OnePlus published
its October 29, 2026 source synchronization for
`CPH2449_16.0.5.1301(EX01)`. A build from that older revision reached device
module compilation but stopped on redundant `MAX`/`MIN` definitions. OnePlus's
`.1301` vendor commit `46a66233a2ce0cf4a9fc61e24ccd158cecfd711f`
contains the corresponding guarded definitions. The integrated revision
`a86dc631f560e67d41f287d92aeab1ddc0991543` is based on that exact official
commit and reapplies the 14 community module-build commits. `git range-diff`
reports every reapplied patch as equivalent (`=`), and the official `.1301`
commit is verified as an ancestor. The pinned manifest is stored at
`c585a9587ba1253ba061098dccbf5b1471b33ef2` in this repository.

The build is not considered successful until the workflow completes, the artifacts are downloaded, their SHA-256 hashes are recorded, the compiled kernel reports `5.15.197`, and a nonpersistent `fastboot boot` canary succeeds on the target device. No persistent partition write is authorized by this build workflow.

Build-attempt evidence:

- Run `43417652353` compiled the 5.15.197 GKI kernel, the `.1301` MSM device
  kernel, and the vendor modules through `modules_install`. It then failed in
  `dtbs_install` when parallel make jobs raced while creating the shared
  `dtb_staging/vendor/oplus` destination. The observed failure was
  `install: cannot create directory .../dtb_staging/vendor/oplus`, followed by
  `Makefile.dtbinst` exit 2. This was a staging race after successful
  compilation, not a source, compiler, or module error.
- The remediation serializes only `dtbs_install`. A dedicated `make_serial`
  helper removes existing make `-j`/`--jobs` arguments and invokes `make -j1`;
  kernel, module, and external-driver compilation retain their parallel job
  settings. No diagnostic is suppressed and no kernel behavior is changed.
- Run `43422510427` completed the pinned 5.15.197 kernel, `.1301` vendor
  modules, serialized DTB installation, `system_dlkm` construction, and AVB
  footer generation. It stopped during `vendor_boot` packaging because the
  generic kernel-kit OOS16 ramdisk manifest requests four modules that are not
  produced by the published `.1301` source.
- The exact stock `.1301` `vendor_boot.img` was independently range-extracted
  from the verified OTA. It is 201326592 bytes with SHA-256
  `592640572FA35999D95F0D0800C4DCE305D6053A9EC0BC682BEA6AB773341AF5`.
  Comparison of its ramdisk with the pinned generic manifest proves that
  `oplus_bsp_smart_freq.ko`, `oplus_bsp_close_loop.ko`, and
  `oplus_bsp_file_read_record.ko` are stale: none exists in the stock image or
  either stock load list. `oplus_sched.ko` exists in stock but is absent from
  both normal and recovery load lists and is not published in the matching
  OnePlus source.
- Rebuilding `vendor_boot` would therefore either omit exact OnePlus
  proprietary content or require redistributing stock binaries. The safer
  installation architecture preserves all stock DLKM/vendor-boot partitions,
  installs only the custom boot kernel, and deploys the matching NetHunter
  driver modules separately. `compile_dlkm=false` still compiles and archives
  the GKI and vendor modules as `gki-modules.tar.gz` and `modules.tar.gz`; it
  skips only generation of replacement DLKM and vendor-boot images.
- Run `43431350109` completed successfully with that architecture, but the
  post-build configuration audit found that Kconfig had silently removed
  `CONFIG_USB_AIRSPY` and `CONFIG_USB_HACKRF` because their parent
  `CONFIG_MEDIA_SDR_SUPPORT` was disabled. That artifact was rejected before
  device testing. The build now enables the parent and fails closed after
  `olddefconfig` if any of the three SDR settings is absent.
- Corrected run `43436405914` at commit
  `cadb9ef14e9c1090b039dfcae6f6ae3eec85b76a` completed successfully. The
  embedded config independently verifies Airspy, HackRF, Bluetooth USB,
  RFCOMM, USB HID gadget, CAN, USB serial, KernelSU, namespaces, seccomp,
  cgroups, and OverlayFS. The generated `Image`, the kernel extracted from
  `boot.img`, and the image in the AnyKernel3 ZIP all have SHA-256
  `E200A4C3424F595BB4CDE723FA1F23917CFCA4075A6AE17F8708F182B003E9AA`.
  The `boot.img` SHA-256 is
  `1C9301C9AA7D36487BDC70EE713828C6F9797C5CA915535195EAD6C89604B95F`.
- All 636 compiled modules were staged together and checked with `depmod -e`
  against the build's `vmlinux.symvers` and `System.map`: zero unknown symbols,
  zero symbol-version disagreements, and zero duplicate filenames. The six
  `depmod -w` messages are duplicate aliases resolving to the same owning
  modules (`nvme`, `oplus_chg`, and `qcom_i2c_pmic`), not ABI failures.
- The separately packaged driver module contains a 72-module dependency
  closure for external Atheros, MediaTek, Ralink, and RTW88 Wi-Fi, SLCAN, and
  USB monitoring. It checks the exact kernel release at install time and does
  not auto-load drivers. The physical-memory read/write `MemKernel` module is
  deliberately excluded because it creates an unrestricted process-memory
  access interface and conflicts with the hardened-device objective.
